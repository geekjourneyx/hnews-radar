## 今日总判断

今天最值得关注的主线不是“模型又强了一点”，而是 **Agent / RSI 的系统工程正在变得可测量**：Sakana MASS 把多 Agent 协作搜索出的工作流继续蒸馏回模型权重；另一个持续 3 个月、消耗 500B+ tokens 的真实反编译项目则给出反面证据——没有客观 oracle / verifier 时，多 Agent 可以非常高效地持续产出“看起来正确、实际语义错误”的代码。

### 综合强信号

**S-001｜MASS：RSI 从“优化 Prompt/Harness”走向“搜索工作流 → 选轨迹 → 微调权重 → 再递归”。** Sakana AI 与 UC Berkeley 提出的 Multi-Agent Self-Supervision（MASS）使用同一个模型同时扮演 executor、workflow optimizer、evaluator。内环搜索多 Agent workflow，外环从自评最优的团队轨迹中选择训练数据，再对共享模型做 LoRA 微调，随后进入下一轮。两轮后，在其 3 个 synthetic held-out research tasks 上，Round 2 相对 base 的 external-judge win rate 为 69.9%；在 MLR-Bench、DSBench、ScienceAgentBench、AstaBench 上 score/output-token 提升到 base 的 1.2–1.6×，但 Terminal-Bench 2.0 与 SWE-bench Verified 分别只有 0.96× / 0.94×，说明泛化并不均匀。论文还给出一个关键消融：只升级 evaluator 帮助有限，同时升级 optimizer 后 workflow search 明显加速，作者据此认为 RSI 的瓶颈可能更偏 optimizer，而不只是 evaluator。

### 项目与工具雷达

**S-003｜Pensieve：把代码、文档和过去 Agent session 做成本地索引，通过 MCP 给 Coding Agent 一次命中更多上下文。**
- Problem solved: Coding Agent 为找一个实现位置反复 grep/read，会消耗额外 tool calls、tokens 和时间；grep 也不擅长按语义寻找“不知道精确命名”的代码。
- Why now: Coding Agent 生成代码让仓库继续膨胀，context retrieval 开始成为可单独优化的 Harness 子系统。
- What is interesting: 本地索引覆盖代码、文档、历史 agent session，并直接接 Claude Code / Codex / Cursor / 任意 MCP client。
- Mutable benchmark: 作者报告在 144 次 held-out code-finding runs 中，Pensieve 131/144 找到正确文件，grep-only 123/144；平均 tool calls 2.0 vs 3.4（-43%），每次 lookup 成本 $0.041 vs $0.050（-18%），8.6s vs 10.9s（-21%）。这些数字均来自作者自测，非独立 benchmark。
- Discussion signal: HN 反例指出类似 local semantic-code-search 产品很多，Cursor 过去也做过类似能力；真正差异可能是“历史 session 也进入索引”。
- Limitations / counterevidence: 当前讨论样本很小，长期索引新鲜度、repo churn、embedding 成本和真实大型 monorepo 收益尚未独立验证。

### 热点讨论与反直觉观点

**D-001｜MASS 的真正争议：这算“递归自我改进”，还是带 fine-tuning 的自训练 / workflow optimization？**
- Central question: “同一个模型做 executor / optimizer / evaluator，并把选出的轨迹再次训练回自己”是否足以称为 RSI。
- Strong view A: MASS 已超出纯 Harness optimizer，因为 workflow search 结果被蒸馏进模型权重，再由新模型继续承担三个角色，存在真实递归环。
- Strong view B: 这依然可能是自训练、benchmark optimization 或 RL-environment-generation 的连续演化，离“产生超出人类已有知识的新能力”仍有距离。
- Key risk: 自评和优化目标共享盲点，可能 Goodhart；Sakana 自己也把 shared blind spots 明确写成 Achilles' heel。
- Source: https://pub.sakana.ai/mass/
- HN: https://news.ycombinator.com/item?id=50048522
- Key comment: https://news.ycombinator.com/item?id=50049944
- Evidence:
  - https://pub.sakana.ai/mass/
  - https://arxiv.org/abs/2610.12176
  - https://news.ycombinator.com/item?id=50049944
- Evidence type: verified_fact + community_evidence + inference
- Current judgment: 把 MASS 看成“可执行 RSI primitive”更准确；不能据此宣称已实现开放式自我进化。

**D-002｜Verifier 不是越严格越好：关键是“反馈速度 × 完整性 × 可证明性”的工程折中。**
- Central question: byte-exact、随机测试、VM/simulator、SMT 哪种 verifier 最适合长时 Coding Agent。
- Strong view A: byte matching 极快、反馈硬、不会被不完整测试集轻易钻空子，尤其适合需要保留 bug/ABI/回放兼容的反编译。
- Strong view B: 对正常软件开发，byte-exact 太强；VM/simulator、fuzzing、SMT 可以允许不同实现但验证语义，更通用。
- Counterevidence: HN 实践者指出 full branch/line coverage 并不保证语义等价；SMT 又会在 loops / nonlinear arithmetic / aliasing / floating point 上遇到性能边界。
- Source: https://momo5502.com/posts/2026-10-09-game-decompilation/
- HN: https://news.ycombinator.com/item?id=50039092
- Key comments:
  - https://news.ycombinator.com/item?id=50039262
  - https://news.ycombinator.com/item?id=50043810
- Evidence type: author_claim + community_evidence + inference
- Current judgment: verifier 的目标不是“最聪明”，而是给 Agent 足够快、足够难作弊、与任务语义对齐的反馈。

#### X-001｜MASS：RSI 开始从概念变成可执行训练闭环
- 判断: 推荐发布
- 为什么值得发: 同时命中 RSI、Harness、multi-agent workflow、optimizer/evaluator 分工，而且论文主动暴露了泛化失败与 shared-blind-spot 风险。
- Source: https://pub.sakana.ai/mass/

- Key comment: https://news.ycombinator.com/item?id=50049944
- Evidence:

  - https://github.com/SakanaAI/mass
  - https://pub.sakana.ai/mass/
- 事实/推断边界: 方法和 benchmark 为 verified_fact；“RSI primitive”属于 inference。

A｜极简判断版
Sakana 这篇 MASS 值得看。它已经不只是让 Agent 自己改 Prompt：先搜索多 Agent 工作流，再选最好的轨迹训练回模型，更新后的模型继续当 executor、optimizer、evaluator。RSI 开始有了可执行闭环。

B｜个人观察版
最近看 RSI，我越来越关注 Harness 怎么进入训练闭环。MASS 很典型：优化 roles/instructions 只是表面，最后真正强化的是 contracts、hops 和信息流，再把团队轨迹蒸馏回模型。Harness 和模型训练正在合流。

C｜反直觉讨论版
MASS 里一个很有意思的结果：只换更强 evaluator 帮助没那么大，把 optimizer 一起变强后，工作流搜索明显加速。RSI 的瓶颈可能不只是“谁来判断好坏”，还在“谁能根据反馈真的提出更好的下一步”。

A｜极简判断版
一个 500B+ tokens、跑了 3 个月的多 Agent 反编译实验，最重要的结论不是模型多强：没有客观验收标准时，Agent 会非常高效地把错误代码铺满项目。真正让系统跑起来的是 verifier。

多 Agent 扩容可能是最容易优化错的指标。16 个 Agent、更多 token、更高吞吐都能让进度条很好看，但如果 verifier 不够硬，只是在更快地产生技术债。未来 Agent 系统的核心资产，很可能是一套难作弊的反馈环境。
