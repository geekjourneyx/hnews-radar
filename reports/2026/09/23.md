### 相比上一轮新增

#### S-001｜GPT-6 Sol / Luna：OpenAI 明确把 Cost / Task 与 Cache 推到 Frontier Agent 的主坐标轴
- **判断**：strong
- **核心信号**：OpenAI 将 Sol / Luna 的 API token 价格相对 GPT-5.6 对应型号下调约 50%，同时在 AutomationBench、DeepSWE、OSWorld 等结果里反复用“cost per task”描述模型价值，而不是只报单一能力分数。
- **Agent / Harness 含义**：官方单独强调 prompt caching，并提供 dashboard、diagnostics、cache breakpoint；reasoning effort 与 tool availability 的调整也可尽量维持此前上下文缓存。
- **非显然点**：HN 讨论很快从“token 单价”转向“完成我的真实任务到底消耗多少 token / cache read”。对于长时 coding agent，高 cache-hit 工作流可能让 cache read 成为主要成本项，因此 $/M tokens 已不足以代表真实经济性。
- **限制**：官方 benchmark 由 OpenAI 自报；不同 harness、provider、缓存策略和实际代码库会显著改变单任务成本。
- **Source:** https://openai.com/index/introducing-gpt-6-sol-and-luna/

#### S-002｜Claude Opus 5.5：Anthropic 同样把 cache read、steps 与长任务经济性放到发布核心
- **判断**：strong
- **核心信号**：Anthropic 官方给出 Opus 5.5 的 cache reads $0.20/M、input $4/M、output $20/M，并称典型 workload 成本较 Opus 5 低约 40%、输出速度提升 30%+。官方也用 codebase-wide migration、HAProxy C→Rust、FrontierCode、Terminal-Bench 等长任务描述模型。
- **Agent / Harness 含义**：官方明确写出 cache reads “make up the majority of agentic and coding work costs”。这说明长上下文 agent 的真实成本结构已经成为模型产品设计的一等指标。
- **HN 争论**：社区同时出现真实 patch-review 小样本与失败案例；同一模型在具体代码审查上的表现差异很大，进一步说明需要 task-specific eval，而不是只看统一榜单。
- **限制**：Anthropic 的“40% cheaper”等结论主要来自官方内部测试和指定 benchmark；HN 实例样本量有限。

#### S-003｜Unreal Agent：Harness Tax 开始被直接产品化优化
- **判断**：strong
- **核心信号**：Unreal Labs 发布 async-first agent harness，把 tool operations 变成异步执行，试图减少模型等待、轮询与 heartbeat 管理产生的模型轮次和 token 消耗；项目同时提供 Go library、runner 与 Harbor benchmark runner。
- **架构价值**：repo 明确拆出 context builder、LLM adapter、tool registry、tool translator、operation manager、session store 等组件；operation manager 支持可替换实现和远程 sandbox 代理，体现 harness 已经是独立工程系统。
- **HN 反证**：高信息量评论指出部分收益可能来自 Codex 当前 polling 行为，可通过配置/patch 降低；也有人指出 OpenAI/Claude 正在吸收 async tool calling，独立 harness 的优势可能被 frontier lab 快速 sherlock。
- **当前判断**：真正强的信号不是“某个新 harness 一定更省 40%”，而是 **tool scheduling / wait policy / cache preservation 本身已经成为可量化优化空间**。

### 项目与工具雷达增量

#### P-001｜JevBench — typed decision model 开始有自己的可复现 eval
- **Problem solved**：Jev 类模型输出 bounded choices + probabilities，不适合直接沿用通用生成模型的文本 benchmark；JevBench 尝试统一评估 intelligence、calibration、speed、cost。
- **Why now**：Jev / typed decision 近期快速扩散，但“快、便宜”很容易掩盖智能不足；当前 v1.3.0 已引入 chance-corrected intelligence 与低智能惩罚。
- **Interesting**：公开 harness、部分 public / held-out 数据、原始结果 artifact，并区分 native probability 与普通 LLM schema verbalized probability。
- **Non-obvious**：Jev 的市场空间更像 harness 内部的 routing / policy / judge / intent / severity 等高频决策层，而非替代通用 frontier model。
- **Discussion signal**：HN 当前约百 points，讨论仍早；真正需要观察的是独立团队能否在真实业务 decision workload 上复现速度/成本优势。
- **Limitations**：Benchmark Heaven 自建 benchmark，仍存在任务选择与 composite 权重带来的设计偏差。
- **Signal class**：worth-watching
- **Share angle**：Jev 真正开始成熟的信号，可能不是又多了一个模型，而是终于出现了适配 typed decision 的独立 eval。
- **Source:** https://github.com/fstandhartinger/jevbench

#### P-002｜Drop — 面向 coding agent 的 rootless 本地 sandbox
- **Problem solved**：本机直接运行第三方程序或 coding agent 时，agent / dependency 可访问真实 home、SSH key、本地服务；VM / container 又会损失本机开发环境便利性。
- **Why now**：coding agent 权限越来越大，本地执行安全开始从“审批 UX”下沉到 OS isolation。
- **Interesting**：Drop 使用 rootless Linux namespaces；可选 gVisor user-space kernel；同一配置可在 native / gVisor runtime 切换。
- **Non-obvious**：agent sandbox 的产品机会并不只在云端 ephemeral VM，本地“virtualenv 式安全边界”也可能是独立层。
- **Discussion signal**：HN 已形成较高质量安全讨论，关注 user namespace、kernel boundary、gVisor compatibility 与真实工作流摩擦。
- **Limitations**：gVisor 有 syscall 性能与兼容性成本；rootless namespace 本身并不等同于完整 VM 安全边界。
- **Signal class**：worth-watching
- **Share angle**：Coding Agent 越来越能干之后，本地 sandbox 可能会像 Python virtualenv 一样变成默认开发习惯。
- **Source:** https://droprun.sh/

### 热点讨论升温 / 分歧变化

#### D-001｜Frontier model 的比较单位正在从 $/token 迁移到 $/task
- **核心问题**：价格下降到底应该看 token 单价，还是完成真实任务所需的全部 token、cache、steps、tool calls 与 wall-clock time？
- **证据 A**：OpenAI GPT-6 发布大篇幅直接报告 cost per task，并强化 cache diagnostics。
- **证据 B**：Anthropic Opus 5.5 明确强调 cache read 在 agentic/coding cost 中的占比，并同时给出任务成本与长任务数据。
- **社区反例**：HN 用户用自己的 coding workflow 指出，同一模型在高 cache-read 场景的真实成本与统一 benchmark 可能差异很大。
- **当前判断**：评价 Frontier Agent 更合理的最小单位正在变成 **task outcome × quality × total cost × elapsed time**。
- **Source:** https://openai.com/index/introducing-gpt-6-sol-and-luna/

#### D-002｜Harness efficiency 从“工程实现细节”升级为模型经济学的一部分
- **核心问题**：同一底模，harness 如何影响总成本与最终质量？
- **观点 A**：异步 tool execution、减少 polling、批量独立工具调用、cache preservation 可以明显降低无效 token 与模型轮次。
- **观点 B**：这些优化容易被 Codex / Claude 等官方 harness 快速吸收，独立 harness 必须继续在 verifier、context routing、sandbox、state、tool discovery 等更深层形成优势。
- **当前判断**：Harness Tax 已经可以被测量，未来 benchmark 需要把 Model × Harness × Tools × Cache policy 一起记录。
