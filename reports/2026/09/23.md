#### P-003｜npunlock — 把 Intel NPU 隐藏的 SHAVE custom-kernel 路径重新拼出来
- **Problem solved**：Intel NPU 的公开软件栈主要面向 graph-level programming；当开发者需要 uncommon operator、高精度 kernel 或把多个小 kernel 融成一个时，缺少公开的“用户 C 代码 → NPU native kernel”工作流。
- **Why now**：项目在 9 月 23 日记录了新的可验证里程碑：同一 native graph 中可运行独立的 FP32-unary 与 FP16-binary custom branches，并通过 explicit ACT-group preflight 处理 compiler branch reordering。
- **What is actually interesting**：项目没有重写整个驱动/编译栈，而是把 Intel graph compiler 当作负责 tensor placement、scheduling、DMA、barrier、invocation environment 的 carrier，再替换特定 ACT range 对应的 SHAVE executable code。这个“保留 vendor compiler，只打开 custom compute slot”的路径工程上很聪明。
- **Contrarian / non-obvious**：Laptop NPU 的开发者价值可能不只在 TOPS 或跑现成模型；一旦 custom kernels 可控，NPU 才更接近通用可编程 accelerator。HN 里做 radio DSP 的实践者也反馈 Intel graph compiler 存在 FP32→FP16 mis-lowering、reshape 成本不稳定等问题，说明更底层控制确有真实工程需求。
- **Discussion signal**：HN 讨论量不大，但已有具体硬件实践反馈；作者明确把 Linux / newer NPU 支持标为 hypothesis，未冒充已验证。
- **Limitations / counterevidence**：目前只验证 Windows x64 + Meteor Lake/NPU3720 + static shapes；依赖旧 OEM driver 包中的 proprietary MoviTools，其他 NPU generation 和 Linux 尚未验证。Intel/OpenVINO 本身已有 framework-level custom operation 扩展，npunlock 的增量在于直接触达该 NPU native execution path，不应泛化成“此前完全不能自定义任何 op”。
- **Signal class**：worth-watching
- **Share angle**：这个只有几十个 HN points 的项目很值得看：它真正解锁的不是一个算子，而是“你买下来的 NPU 到底能不能自己写 kernel”。

- **Problem solved**：把大 OpenAPI spec 直接展开为数百个 MCP tools 会占用大量上下文；API 返回的大 JSON 也会继续吞 token，并增加 agent 选错工具和误执行 mutation 的风险。

### 热点讨论升温 / 分歧变化

#### D-003｜“Jev 25 行 Python”真正把争论从 API 形式推到了 calibration / latency / error rate
- **核心问题**：如果任意小 LLM 都能取候选 token logits、softmax 成 probabilities，Jev / typed decision model 还有多少技术壁垒？
- **观点 A：接口层并不新**。NobodyWho 用 Qwen3-0.6B + llama.cpp 在约 25 行 Python 中演示 bounded labels → logits → probabilities；HN 里还有实践者说明自己早已用 logprob + option permutation 做高分辨率 A/B classifier。
- **观点 B：真正难点不在“能输出概率”**。反方强调普通 chat model 的 logits 可能被 prose tendency、tokenization、选项顺序偏置污染；更关键的是 probabilities 是否 calibration、45 个问题批量时的 latency / throughput、malformed rate 和真实 error rate。TypeSafe 自己的文档也明确区分 probabilities 与 confidence；经典 calibration 研究说明现代神经网络天然可能过度自信。
- **相比上一轮新增**：P-001 JevBench 的价值反而被这场争论强化——没有 accuracy × calibration × speed × cost 的可复现 workload benchmark，“25 行复刻”与“frontier decision intelligence”都很难证伪。
- **当前判断**：Jev 的最小产品形态很容易复制，不能把 typed output / probability API 当 moat；可能存在的护城河集中在 domain-general calibration、post-training、batched inference economics 与独立 benchmark 上。今天没有足够证据证明 Jev 已建立这些壁垒，也没有证据证明 25 行 demo 等价复现了 Jev 的实际性能。

### 今日最终判断

1. **今天最强的趋势不是“又有两个更强模型”，而是 Agent 经济性进入可工程化阶段。** Cost/task、cache hit、tool scheduling、wait policy、context size、sandbox 都开始直接决定任务成本与可用性；模型与 harness 需要一起测。
2. **Jev 方向仍值得跟踪，但评价标准需要明显提高。** “单 token / typed probabilities / 低延迟”只能说明接口形态；真正需要看 calibration、真实 error rate、并发吞吐、成本与独立 workload eval。JevBench 的重要性因此高于任何“25 行复刻”的传播热度。
3. **低热度工具里最值得继续追的是 control plane。** npunlock 打开本地 NPU custom-kernel 控制，PostMCP 管 MCP tool/context 控制，Drop 管本地 agent 权限边界，Unreal Agent 管 tool scheduling——共同指向一个方向：Agent / AI 工程的价值正在向“谁能更好控制执行、上下文、权限与成本”迁移。
