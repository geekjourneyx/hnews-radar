### 相比上一轮新增

#### S-001｜MiMo-V2.6：模型发布之外，更强的信号是“后训练过程可观察化”
- **判断**：strong
- **核心信号**：MiMo-V2.6 在 HN 约 15 小时内达到 900+ points / 400+ comments。讨论里最有信息量的部分不是榜单排名，而是其公开 RL dashboard 暴露出的训练状态、重启原因、staleness / KL 等指标，使外部工程师可以观察后训练系统的真实动态。
- **反直觉点**：公开 dashboard 并不等于训练可复现或数据透明；它更像“训练系统 observability 的公开接口”。真正稀缺的信息仍包括训练数据、环境细节与完整复现实验。
- **Source:** https://mimo.xiaomi.com/mimo-v2-6
- **HN:** https://news.ycombinator.com/item?id=49792730

#### S-002｜AI coding 的下一个瓶颈开始落到 CI / verification
- **判断**：strong
- **核心信号**：Linear 明确把 AI coding 之后的 CI 等待与 runner 成本列为工程瓶颈；其公开数据称，年初以来测试套件接近 4 倍增长，同时 PR CI 等待从 6+ 分钟压到略高于 5 分钟，并把每测试 runner time 约减半。
- **真正重要**：当生成代码的边际成本下降，验证吞吐、测试选择、环境启动、缓存、增量执行、失败定位会成为新的“开发者速度税”。
- **HN 争论**：一派质疑“开发更快为何用户没看到更多功能”；另一派给出的真实案例是 AI 先吞掉 tech debt、QA、审计、运维等隐性工作，收益未必先表现为 feature velocity。
- **Source:** https://linear.app/now/ci-bottleneck-reworked
- **HN:** https://news.ycombinator.com/item?id=49792067
- **Evidence:**
  - https://news.ycombinator.com/item?id=49793932
  - https://linear.app/now/ci-bottleneck-reworked
- **Evidence type:** verified_fact + community_evidence + inference

#### S-003｜RRSI：开始系统化优化 agent harness，而不是只调模型
- **判断**：strong
- **核心信号**：RRSI 将 harness 自改进做成一个受正则约束的搜索过程：proposer 控制每轮修改预算并鼓励探索；selector 使用 critic + pruner 抑制 benchmark-specific、过小、过贵或已失效的改动。
- **论文自报结果**：8 个 benchmark 上，在 evolution split 最高提升 14.1 points，5 个 OOD benchmark 最高提升 4.7 points，同时相较未正则化 evolution 少用约 30% policy tokens。
- **为什么值得关注**：这直接对应当前 coding agent 的核心工程问题——如何让 harness 自动改进，同时避免只对当前 eval 过拟合。
- **限制**：以上 benchmark 结果来自论文作者，尚需独立复现；当前 HN 讨论刚出现，社区证据不足。
- **Source:** https://arxiv.org/abs/2609.24972
- **HN:** https://news.ycombinator.com/item?id=49799183
- **Evidence:**
  - https://github.com/google-research/rrsi
  - https://regularized-rsi.com/
  - https://arxiv.org/abs/2609.24972
- **Evidence type:** author_claim + verified_fact + inference

### 项目与工具雷达增量

#### P-001｜all-your-agents — harness-neutral 的本机 agent session 观察层
- **Problem solved**：当 Codex / Claude Code / OpenCode 等多个 agent 同时运行，缺少统一的 session 状态、等待原因、子 agent 与活动流观察接口。
- **Why now**：多 agent 并行正在让“谁在跑、谁卡住、谁等权限、谁启动了 subagent”成为新的本地开发运维问题。
- **Interesting**：项目把状态统一为 running / waiting / idle，并区分 waitingFor shell / monitor 与真正“需要用户输入”；同时暴露 session / subagent 事件流。
- **Non-obvious**：多 agent UX 的关键可能不是再造一个 agent，而是先做跨 harness 的 control plane / observability layer。
- **Discussion signal**：刚发布到 HN，1 point，尚无有效讨论；低热度不作为降权理由。
- **Limitations**：目前主要证据来自仓库自述，缺乏独立 adoption。
- **Signal class**：early-potential
- **Share angle**：当所有 coding agent 都能跑起来后，下一个缺口可能是“看懂所有 agent 正在干什么”。
- **Source:** https://github.com/markwylde/all-your-agents

#### P-002｜System Design Atlas — 把系统设计从静态笔记变成交互式 trade-off 阅读器
- **Problem solved**：传统 system design 学习材料常停留在长文/静态图，难以把架构节点、trade-off、规模变化与面试追问绑定。
- **Why now**：AI 能快速生成“答案”，但结构化工程判断与 trade-off 训练反而更重要。
- **Interesting**：内容全部是 Markdown，构建时静态生成；Mermaid flowchart 被解析后改用 React Flow 呈现，可点击节点查看 purpose / trade-off / connections；还支持同一设计在 Today vs 100x scale 的演进标签。
- **Non-obvious**：优秀技术教育产品的增量可能不在“更多内容”，而在把 architecture diagram 变成可探索的数据结构。
- **Discussion signal**：刚发布，HN 暂无实质评论。
- **Limitations**：当前 repo 体量和用户 adoption 尚早，主要验证的是产品表达与内容架构。
- **Signal class**：early-potential
- **Share angle**：这个项目最值得抄的不是 system design 内容，是“把 Mermaid 变成可交互工程知识图”的产品结构。

#### P-003｜JetBrains Air — 从 agentic IDE 向组织级 agent development system 延伸
- **Problem solved**：单个 agent 会写代码之后，组织还要处理共享 context、cloud agents、automation、governance、成本与执行控制。

### 热点讨论升温 / 分歧变化

#### D-001｜MiMo 的透明度：是真透明，还是更高级的 observability theater？
- **核心问题**：公开 RL dashboard 能提升多少可验证性？
- **观点 A**：工程师能从 staleness、KL、checkpoint、restart 原因等看到过去只有内部团队能看到的训练动态，教育价值极高。
- **观点 B**：dashboard 仍不能证明数据来源、完整训练流程与独立复现，因此不能把“可观察”误写成“可验证”。
- **当前判断**：把它视为“训练过程的 observability 标准提升”最稳妥；不要扩张成“完全透明训练”。
- **Source:** https://mimo.xiaomi.com/rl/
- **HN:** https://news.ycombinator.com/item?id=49792730
- **Evidence:**
  - https://news.ycombinator.com/item?id=49793855

#### D-002｜AI 开发“速度提升”为什么没有等比例变成更多新功能？
- **核心问题**：代码生成吞吐暴涨后，收益究竟流向哪里？
- **观点 A**：如果产品外部变化不明显，可能只是工程团队跑得更忙。
- **观点 B**：真实收益先流向 tech debt、QA、运维、审计、隔离、内部工具和可靠性，这些不会全部出现在 changelog。
- **当前判断**：更合理的衡量方法应从“代码量 / feature 数”转到 lead time、verification cost、incident rate、operational toil、质量与单位交付成本。
- **Source:** https://linear.app/now/ci-bottleneck-reworked
- **HN:** https://news.ycombinator.com/item?id=49792067
- **Evidence:**
  - https://news.ycombinator.com/item?id=49793932
- **Evidence type:** community_evidence + inference

### 今日最终判断

1. **Harness 正在从外围胶水层升级为可优化对象。** RRSI 已经把 harness evolution、critic、pruner、OOD 泛化放到同一研究框架；all-your-agents 则从工程侧暴露出跨 harness session observability 的新需求。
2. **Verification / CI 会吃掉 AI coding 的下一波红利。** 当生成速度越来越快，测试、环境、缓存、失败诊断、权限与 reviewer attention 会成为主要约束。
3. **“公开训练过程”可能成为模型发布的新竞争维度。** MiMo 的 dashboard 证明公开 observability 本身就能产生强社区信号，但数据透明与可复现仍是另一层门槛。
4. **传统 IDE 厂商正在重构产品边界。** JetBrains Air 的方向已经从“AI 功能”扩到 agent execution / context / governance / cost control；成败仍取决于稳定性和真实 adoption。
